# RFP Compass — 해커톤 아이디어 기획서

- 부제: 300쪽 제안요청서를 3시간 안에 읽는 제안 검토 에이전트
- 한 줄 요약: RFP PDF를 넣으면 요구사항 추적표, 배점 기준 목차 초안, 위험 조항 경고, 제안서 초안 커버리지가 원문 인용과 페이지 번호를 달고 나온다.
- 팀 역할(이름은 선정 후 기입): 제안·영업 경험자(도메인, 골든셋), 백엔드(파서·파이프라인), AI 엔지니어(프롬프트·평가), 프런트(데모 화면·발표)
- 데모 데이터 고지: 데모에 쓰는 RFP는 가상의 기관·사업으로 만든 문서다. 실제 RFP를 쓸 때는 조달청 나라장터에 공개된 자료만 쓴다.

심사 기준에 대한 답

| 기준 | 답 |
| --- | --- |
| AI 활용 수준 | LLM은 "읽기·판단" 단계만 맡고, 흐름·검증·출력은 결정적 코드가 쥔다. 결과는 구조화 출력(pydantic 스키마)으로 받고, 모든 항목에 원문 인용과 페이지를 붙인다. |
| 문제 해결 방식 | 위험 조항은 규칙 20개와 LLM의 이중 판정, 정확도는 골든셋 평가 루프로 올린다. 사람은 결과를 만드는 대신 확인한다. |
| 실제 업무 적용 가능성 | 산출물이 제안 팀이 지금 쓰는 엑셀·워드 형식이다. 사내 FabriX, Claude Enterprise 위에서 그대로 돌릴 수 있다. |

## 1. AI로 해결하고자 하는 문제 상황 또는 새롭게 시도해 보고 싶은 업무/서비스는 무엇인가요?

### 지금의 일

공공·금융 제안을 할 때마다 제안 팀은 200~300쪽짜리 제안요청서(RFP)를 받는다. 입찰 공고 뒤 제안서 제출까지 보통 2~4주다. 그 첫 며칠은 여러 사람이 RFP를 나눠 읽고 요구사항을 엑셀로 옮기는 데 쓴다. 요구사항은 "SFR-001" 같은 고유번호가 붙은 표에도 있지만, 사업 개요나 추진 방향 문단 속에 "~하여야 한다" 형태로 숨어 있는 것도 많다. 표는 옮겨 적어도 문단 속 요구사항은 자주 빠진다.

Loopio의 2025년 보고서(1,544명 조사)에 따르면 RFP 1건에 응답하는 데 평균 25시간, 9명이 든다(단일 출처). 2026년 공공 소프트웨어·ICT장비·정보보호 사업 수요는 6조 4,737억 원이다(과학기술정보통신부 수요예보). 제안 한 건 한 건이 이 시장의 입구다.

### 놓치면 생기는 일

RFP 뒤쪽 계약 조건 장에는 수주 뒤 손실로 이어지는 조항이 있다. 지체상금률이 기준보다 높거나, 하자보수 기간이 3년이거나, "발주기관이 필요하다고 인정하는 경우 과업을 추가할 수 있다"는 문장이 그것이다. 제안 단계에서 이 조항을 보지 못하면 협상 테이블에 올리지 못한다. 계약 뒤에 발견하면 이미 늦다. 제안 PM은 요구사항 표를 채우느라 바쁘고, 계약 조건을 읽는 사람은 따로 없는 경우가 많다.

### 하고 싶은 일

RFP PDF 한 개를 넣으면 다음 네 가지가 나오게 한다.

1. 요구사항 추적표: 표 안의 요구사항과 본문에 숨은 요구사항을 모두 찾아 공공 SW 요구사항 분류 11종(SFR 기능, PER 성능, SIR 시스템장비, INR 인터페이스, DAR 데이터, TER 테스트, SER 보안, QUR 품질, COR 제약, PMR 프로젝트관리, PSR 프로젝트지원)으로 나누고, 필수 여부와 원문 인용, 페이지를 붙인다.
2. 위험 조항 경고: 계약 조건에서 위험 조항을 찾아 추출한 값과 기준값, 왜 위험한지, 협상 때 무엇을 요구할지를 쓴다.
3. 배점 기준 목차 초안: 평가 배점표를 읽어 배점 비중에 비례한 분량의 제안서 목차를 만들고, 각 장에 답해야 할 요구사항 번호를 붙인다.
4. 제안서 초안 커버리지: 작성 중인 제안서 초안을 넣으면 요구사항마다 충족·부분·누락을 판정하고, 필수 요구사항의 누락을 먼저 보여 준다.

사람은 읽고 옮기는 대신 확인하고 결정한다. 이것이 바꾸고 싶은 업무 경험이다.

## 2. 제안한 아이디어를 실현하기 위해 AI를 어떻게 활용할 계획인가요?

### 설계 원칙: 결정적 코드가 흐름을 쥐고, LLM은 읽기와 판단만 맡는다

LLM에게 "이 RFP를 분석해 줘"라고 통째로 맡기면 결과가 매번 다르고 무엇을 놓쳤는지 알 수 없다. 그래서 파이프라인을 여섯 단계로 나누고, 단계 사이의 데이터 형식을 pydantic 스키마로 고정했다. LLM은 그중 세 단계(추출, 위험 보강, 커버리지 판정)에서만 쓰고, 나머지는 코드가 한다.

| 단계 | 하는 일 | LLM 사용 |
| --- | --- | --- |
| parse | pdfplumber로 페이지 텍스트와 표를 뽑고, 제목 패턴으로 섹션을 나눈다 | 없음 |
| extract | 섹션 단위로 Claude에 보내 요구사항을 구조화 출력으로 받는다. 원문 인용이 실제 페이지에 있는지 코드가 재검증한다 | Claude(구조화 출력) |
| toc | 배점표를 코드가 먼저 찾고(배점 열 합 60~100), 요구사항을 배점 항목에 연결해 분량 비례 목차를 만든다 | 연결 단계만 Claude |
| risk | 규칙 20개(정규식+임계값)가 조항 위치를 찾고, Claude가 문맥을 읽어 심각도·근거·협상 포인트를 보강한다 | 보강 단계만 Claude |
| coverage | 초안을 문단 단위로 쪼개 id를 붙이고, 요구사항마다 충족·부분·누락과 근거 문단 id를 받는다 | Claude |
| export | 엑셀(4개 시트), 워드(목차 초안), HTML 대시보드로 낸다 | 없음 |

### AI를 쓰는 방식 네 가지

1. 구조화 출력. Claude(Opus 5.5 기본)의 구조화 출력 기능으로 요구사항·위험·커버리지를 pydantic 스키마 그대로 받는다. 분류는 11종 중 하나로 강제되고, 필수 여부는 must/should/may 세 값만 허용한다. 모델이 자유 문장으로 답할 여지를 없앴다.
2. 원문 인용 강제. 요구사항과 위험 조항은 모두 원문 인용(quote)과 페이지를 가진다. 인용문이 그 페이지 텍스트에 실제로 있는지 코드가 확인하고, 없으면 신뢰도를 낮추고 표시한다. 심사위원이 "그 조항 어디 있어요?"라고 물으면 페이지를 바로 연다.
3. 규칙과 LLM의 이중 판정. 위험 조항은 규칙이 "어디"를, LLM이 "왜·얼마나"를 맡는다. 법령 기준값(지체상금률 1000분의 1.25, 하자담보 1년, 계약보증금 10%)은 코드가 아니라 규칙 파일에 근거 조문과 함께 둔다. 규칙에 걸리지 않은 위험을 LLM이 추가로 올리면 "검토 권고"로 따로 표시한다.
4. 골든셋 평가 루프. 샘플 RFP에 정답 요구사항과 심어 둔 위험 조항 목록을 만들어 두고, 추출 재현율·정밀도와 위험 탐지율을 매번 측정한다. 지표가 떨어지면 원인이 표 파싱인지 프롬프트인지 가른 뒤 한 가지만 고치고 다시 잰다.

### 개발 하네스: 서브에이전트 7개와 스킬 3개

파이프라인을 48시간 안에 만들고 고치기 위해 Claude Code 안에 역할이 나뉜 서브에이전트를 둔다. 각 에이전트는 맡는 모듈, 지키는 원칙, 검증 방법이 정해져 있다.

| 에이전트 | 역할 | 맡는 모듈 |
| --- | --- | --- |
| rfp-orchestrator | 여섯 단계 실행과 체크포인트 확인, 실패 시 재개 지점 결정 | pipeline.py, cli.py |
| rfp-parser | 표 행 수와 페이지 번호가 원본과 같은지 책임 | parse.py |
| requirement-extractor | 표와 본문의 요구사항 추출, 인용 재검증, 중복 병합 | extract.py |
| toc-architect | 배점표 인식과 분량 비례 목차 생성 | toc.py |
| risk-auditor | 위험 규칙 유지와 LLM 보강 판정 | risk.py, risk_rules.yaml |
| coverage-checker | 제안서 초안 대조 | coverage.py |
| eval-judge | 골든셋 측정과 개선 제안 한 가지 | eval/ |

스킬은 `/rfp-review`(전체 실행과 요약), `/risk-rules`(규칙 추가 절차와 예문 테스트), `/demo-rehearsal`(3분 데모 점검표) 세 개다. 사내에서는 FabriX 또는 Claude Enterprise 위에서 같은 구조로 돌릴 수 있다.

## 3. 해커톤 2일 동안 구현해보고 싶은 주요 기능은 무엇인가요?

### 핵심 기능 네 가지

| 기능 | 사용자가 하는 일 | AI가 보여 주는 것 |
| --- | --- | --- |
| ① 요구사항 추적표 | RFP PDF를 올린다 | 요구사항 목록(ID, 11종 분류, 필수 여부, 원문 인용, 페이지). 본문에서 찾은 요구사항은 "본문" 배지로 구분 |
| ② 위험 조항 경고 | 위험 카드를 연다 | 조항 원문, 추출값과 기준값(예: 지체상금률 0.25%/일 vs 기준 0.125%/일), 왜 위험한지, 협상 포인트 |
| ③ 배점 기준 목차 초안 | 제안서 총 분량을 입력한다 | 배점 항목별 장과 배정 분량, 각 장에서 답할 요구사항 번호, 두 문장짜리 작성 지침. 워드로 다운로드 |
| ④ 제안서 초안 커버리지 | 작성 중인 초안(md/docx)을 올린다 | 요구사항마다 충족·부분·누락과 근거 문단. 필수 요구사항 누락 건수를 맨 위에 빨간색으로 |

### 데모 흐름(3분)

| 시각 | 화면 | 말하는 것 |
| --- | --- | --- |
| 0:00 | RFP PDF 업로드, 6단계 진행 바 | 300쪽 RFP, 평균 25시간·9명이 읽던 일(Loopio 2025) |
| 0:30 | 요구사항 추적표 | 표뿐 아니라 본문에 숨은 요구사항을 찾았다. 하나를 클릭해 원문 페이지를 연다 |
| 1:15 | 위험 조항 경고 | 높음 등급 조항 하나를 읽는다. 추출값과 기준값을 나란히 보여 준다 |
| 2:00 | 배점 기준 목차 초안 | 심사위원은 배점표 순서로 읽는다. 배점·분량·연결 요구사항 |
| 2:30 | 초안 커버리지 | 필수 요구사항 누락 건수를 빨간색으로 |
| 2:50 | 엑셀·워드 다운로드 | 내일 아침 제안 PM 책상에 올라가는 파일 |

### 48시간 계획

- Day 1 오전: 가상 RFP PDF 생성(요구사항 표 + 본문 숨은 요구사항 + 심은 위험 조항), 골든셋 작성. 파서(pdfplumber) 완성.
- Day 1 오후: 요구사항 추출(구조화 출력, 인용 재검증, 중복 병합), 위험 규칙 엔진 20개 + 예문 테스트. 첫 재현율 측정.
- Day 2 오전: 배점표 인식과 목차 초안, 초안 커버리지, 엑셀·워드 출력.
- Day 2 오후: 대시보드 화면, 녹화본 준비, 리허설 2회, 발표 자료.

범위 밖: 스캔본 OCR, 실시간 협업 편집, 제안서 본문 자동 작성.

## 4. 이 아이디어의 주요 사용자는 누구이며, 어떤 기대효과가 있나요?

### 사용자

- 1차: 제안 PM과 제안서 작성자. RFP를 처음 받은 날 추적표와 목차 초안을 손에 쥔다.
- 2차: 사업관리(PMO)와 법무·계약 검토자. 위험 조항 목록을 받아 협상 전략을 세운다.
- 3차: 영업. 입찰 참가 자격과 위험 조항을 보고 참여 여부를 빨리 결정한다.

### 기대효과(측정 전이므로 목표로 적는다)

| 영역 | 지금 | 목표 |
| --- | --- | --- |
| 업무 효율 | RFP 1차 검토에 며칠, 여러 명 | 1차 검토 3시간 이내. 사람은 확인과 결정에 시간을 쓴다 |
| 오류 감소 | 본문 속 요구사항 누락, 계약 조건 미검토 | 필수 요구사항 누락 0건, 위험 조항을 제안 단계에서 협상 테이블에 올림 |
| 정보 접근성 | 요구사항과 조항이 PDF 속에 묻힘 | 모든 항목에 페이지와 원문 인용. 누구나 10초 안에 원문 확인 |
| 고객 가치 | 배점표와 어긋난 목차 | 배점 비중에 맞춘 목차로 평가자가 읽기 쉬운 제안서 |

### 확산

사내 7대 메가 프로세스 가운데 영업 프로세스에 먼저 적용하는 "클라이언트 제로" 방침에 맞는다. 제안 팀이 내일부터 쓸 수 있는 엑셀·워드가 나오고, 그다음 단계로 FabriX 에이전트로 올려 고객사 제안 조직에도 제공할 수 있다.

### 차별점

문서 요약이나 범용 Copilot은 "이 문서가 무슨 내용인가"를 답한다. RFP Compass는 제안 업무의 순서를 따른다. 배점표 순서로 목차를 짜고, 초안을 요구사항과 대조하고, 계약 조건을 기준값과 비교한다. 이 세 흐름은 제안 업무에서만 나온다.

### 위험과 대응

| 위험 | 대응 |
| --- | --- |
| 참신함이 낮아 보인다 | 배점 기준 목차와 초안 대조를 데모 중심에 둔다 |
| LLM이 틀린다 | 모든 결과에 원문 인용과 페이지가 있어 사람이 10초 안에 확인한다. 규칙에 없는 LLM 단독 판단은 "검토 권고"로 구분한다 |
| 실제 RFP 사용 | 데모는 가상 RFP. 실제 문서는 나라장터 공개 자료만 쓰고 출처를 첫 장에 적는다 |
| 라이브 데모 실패 | 체크포인트에서 출력 단계만 다시 돌리는 명령과 같은 시나리오의 녹화본을 준비한다 |
