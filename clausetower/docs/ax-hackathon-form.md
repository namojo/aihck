# AX해커톤 아이디어 기획서 — ClauseTower (계약을 읽는 물류 관제탑)

> 양식의 7개 문항에 맞춰 적었다. 숫자는 이 저장소의 실행 결과(`README.md` 측정 결과, `eval/results/`)에서 가져왔고, 측정하지 않은 값은 "목표"로 표시했다.

## 1. AI로 해결하고자 하는 문제 상황 또는 새롭게 시도해보고 싶은 업무/서비스는 무엇인가요?

태풍, 항만 적체, 창고 시스템 장애 같은 교란이 생기면 물류 운영팀은 **마감이 급한 화물부터** 보낸다. 그런데 같은 1시간 지연이라도 고객마다 물리는 돈이 전혀 다르다. 어떤 계약은 24시간 유예가 있고, 어떤 계약은 지연 1건당 50만 원 정액이 바로 물리고, 어떤 계약은 태풍이 면책 사유지만 "12시간 이내 서면 통지"나 "대체 운송 노력 입증" 조건을 못 채우면 면책이 사라진다.

이 조건들은 고객별 계약서 PDF 수십 쪽 안에 흩어져 있어서 사건이 터진 순간 아무도 꺼내 보지 못한다. 결과적으로 **급한 화물을 먼저 보내고, 정작 돈이 물리는 화물은 뒤로 밀리며, 받을 수 있었던 면책은 통지 시한을 놓쳐 날린다.** 사후에 법무·영업이 페널티 정산을 할 때야 "그 조항이 있었네"를 알게 된다.

시도하려는 것은 **계약서를 읽어 사건별 실제 노출액(exposure)을 계산하고, 그 값으로 배차 우선순위를 바꾸며, 지금 당장 해야 할 조치(어느 화물을 먼저, 어느 고객에게 몇 시간 안에 통지, 어떤 입증 자료를 확보)를 원문 인용과 함께 제시하는 관제 서비스**다.

## 2. 제안한 아이디어를 실현하기 위해 AI를 어떻게 활용할 계획인가요?

AI와 코드의 역할을 분명히 나눈다. **LLM은 읽고 판단하고, 코드가 계산하고, 시뮬레이터가 심판한다.**

| 단계 | 누가 | 무엇 |
| --- | --- | --- |
| 계약 조건 추출 | Claude (구조화 출력, pydantic 스키마) | 계약서 전문 → 과금 방식(시간당·일당·누진·건당 정액), 요율, 유예, 상한과 범위, 불가항력 사유, 통지 시한, 정성 조건. 항목마다 **조항 번호와 원문 인용**을 함께 내고, 인용이 원문에 글자 그대로 있는지 코드가 검증한다 |
| 면책 판단 | Claude | 이번 사건 설명 × 계약 조항 → 사유 해당 여부, 통지 충족 여부, 조건별 충족 여부. 최종 적용 여부는 LLM이 아니라 코드가 `조항 있음 ∧ 사유 해당 ∧ 통지 충족 ∧ 조건 충족`으로 기계적으로 결합한다 |
| 노출액 계산 | 결정적 코드 | 유예·단위 올림·누진·상한·불가항력을 적용해 "지금 보내면 / 한 사이클 미루면" 페널티를 원 단위로 계산 |
| 배차 우선순위 | 결정적 시뮬레이터 | 트럭 점유 1시간당 추가로 물리는 돈(한계 노출)이 큰 화물부터. 기존 마감 순, 도착 순, 고액 순, 지역 탐색 근사 최적과 나란히 비교 |
| 조치 제안 | 코드 + 인용 | 통지 시한이 남은 고객, 조건만 채우면 면책이 살아나는 고객과 그 금액, 지금 보낼 화물 3건을 원문 인용과 함께 표시 |

LLM 연결은 세 경로를 모두 지원한다. Anthropic API 키, Claude 구독(Claude Code CLI를 로컬 도우미로 호출), 사내 LLM(OpenAI 호환·Anthropic 호환 엔드포인트). 계약서 본문은 선택한 LLM 외에는 어디에도 전송하지 않는다.

## 3. 해커톤 2일 동안 구현해 보고 싶은 주요기능은 무엇인가요?

이미 동작하는 프로토타입(`github.com/namojo/clausetower`, 데모 `namojo.github.io/clausetower`)이 있으므로 2일은 다음에 쓴다.

1. **실제 계약서 형식 대응.** 지금은 txt·md·docx만 받는다. PDF(스캔본 OCR 포함)와 HWP 업로드, 수십 쪽 계약서에서 지체상금·면책 조항만 찾아내는 사전 분할을 넣는다.
2. **조치 보드.** 사건이 들어오면 "지금 보낼 화물 3건 / 지금 보낼 통지(고객·시한·남은 시간) / 조건만 채우면 살아나는 면책과 금액"을 한 화면 맨 위에 두고, 버튼 한 번으로 통지 문안 초안(조항 인용 포함)을 만든다.
3. **배차 엔진 연동 형태 정리.** 기존 TMS·배차 엔진을 바꾸지 않고 "한계 노출(원/시간)" 열 하나를 우선순위 입력으로 넘기는 API와, 사람이 최종 판단을 뒤집는 승인 흐름.
4. **평가 루프.** 팀이 만든 정답지(계약 8부·판단 32항목)와 다중 시드(30개) 견고성 평가를 CI에 올리고, 프롬프트나 모델을 바꿀 때 정확도가 떨어지면 막는다.

## 4. 이 아이디어의 주요 사용자는 누구이며, 어떤 기대효과가 있나요?

**주요 사용자**

- 물류·운송 **관제/배차 운영자**: 교란 발생 직후 몇 시간 안에 순서를 정하고 고객에게 통지하는 사람.
- **계약·영업 담당자**: 고객별 페널티 조건을 관리하고 사후 정산에서 분쟁을 겪는 사람.
- 확장하면 제조 납기(지체상금), IT 운영 SLA 크레딧, 건설 공정 지체상금처럼 "계약 조항 × 운영 사건 → 돈"인 모든 B2B 운영 조직.

**기대효과(측정값과 목표를 구분)**

| 항목 | 값 | 출처 |
| --- | --- | --- |
| 같은 화물·같은 교란에서 순서만 바꿨을 때 총 페널티 절감 | 시나리오 3종 58~77%, 시드 30개 × 3종 90/90 승(평균 58.7~69.1%) | `eval/results/robustness.md` (가상 시뮬레이터, 측정) |
| Claude의 계약 조건 추출 정확도 | 106항목 중 96.2%, 인용 원문 일치 100% | `eval/results/extraction_*.json` (측정) |
| 면책 판단 정확도 | 태풍 100%, 항만 적체 96.9% | 같은 파일 (측정) |
| 계약 8부 읽기 비용·시간 | 24회 호출, $1.98, 병렬 4개로 270초 | 실행 로그 (측정) |
| 통지 시한 미준수로 날리는 면책 0건 | 목표 | 조치 보드가 시한을 카운트다운 |
| 사후 페널티 정산 분쟁 감소 | 목표 | 모든 판단에 조항 번호·원문 인용 |

## 5. 아이디어가 구현된 모습을 한 줄로 요약하면 어떤 모습일까요?

**태풍이 상륙한 아침, 관제 화면 맨 위에 "지금 보낼 화물 3건, 지금 보낼 통지 2건(남은 시간 포함), 입증 자료만 챙기면 살아나는 면책 84만 원"이 계약서 조항 번호와 함께 떠 있고, 배차 순서는 급한 순이 아니라 물리는 순으로 이미 바뀌어 있다.**

## 6. 아이디어 구현에 필요한 데이터가 있나요?

| 데이터 | 해커톤에서 | 실제 적용 시 |
| --- | --- | --- |
| 고객별 운송 계약서(지체상금·면책 조항) | 가상 고객 8곳의 계약서 8부를 직접 작성해 사용. 형식·조항 구조는 공공 표준계약서와 실무 관행을 따랐다 | 고객사 계약서 원본(PDF/HWP). 민감 문서이므로 사내 LLM 또는 로컬 도우미 경로로 처리 |
| 조건 정답지 | 계약 8부 × 항목 106개, 사건 3종 × 판단 32항목을 팀이 작성 | 법무 검수를 거친 정답지로 교체 |
| 화물·노선·트럭 운영 데이터 | 허브 1곳, 노선 8개, 트럭 8대, 화물 56건의 결정적 시뮬레이터(시드 30개) | TMS/WMS의 주문·배차·실적 데이터 |
| 사건 데이터 | 태풍, 항만 적체, WMS 장애 시나리오 3종(결항 대수, 노선 지연 배율, 통지 시점, 입증 여부) | 관제 시스템의 장애·기상 이벤트, 통지 기록 |

개인정보는 쓰지 않는다. 실제 계약서로 시연할 때는 저장소에 넣지 않고 출처를 밝힌다.

## 7. 제안해 주신 아이디어에 대해 추가로 언급하고 싶은 내용이 있으면 작성해 주세요.

- **이미 돌아간다.** 파이썬 파이프라인(39개 테스트), 브라우저 안에서 같은 계산을 하는 웹 데모(파이썬과 31개 항목 숫자 일치 검증), 실제 Claude 실행 보고서와 로그가 저장소에 있다. 심사장에서 오프라인으로 열리는 단일 HTML 대시보드도 있다.
- **선행 사례를 찾아봤다.** 계약 분석 도구(CLM)는 조항을 "찾아 주고", 배차 최적화 도구는 마감과 거리로 "순서를 정한다". 둘을 이어 **계약 조항을 사건별 노출액으로 바꿔 운영 순서를 바꾸는 것**, 그리고 한국어 지체상금 맥락(역일·영업일·누진·정액·통지 시한·입증 조건)을 다루는 것은 찾지 못했다.
- **돈 계산을 LLM에 맡기지 않는다.** LLM의 역할을 "읽기와 판단"으로 제한하고 결합과 계산은 코드가 하기 때문에, 틀렸을 때 어디가 틀렸는지 항목 단위로 추적되고 사람이 뒤집을 수 있다. 사람이 뒤집은 판단은 화면에 "사람 결정"으로 남는다.
- **한계.** 시뮬레이터가 작고(노선 8개, 트럭 8대), 정답지를 같은 팀이 만들었으며, PDF·HWP 입력이 아직 없다. 이 셋이 2일 동안의 과제다.
