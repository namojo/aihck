# ClauseTower 기획서 — 계약을 읽는 물류 관제탑

> 구호: **마감 임박 순이 아니라, 배상 노출 순으로.**
> 한 줄: 물류 지연이 터졌을 때 고객별 계약서의 지체상금·SLA 조항을 실제로 읽어 "지금 이 순간 어느 계약의 배상금이 실제로 발생하는가"를 계산하고, 그 노출액 순서로 배차를 다시 짜는 에이전트.

문서의 숫자는 모두 이 저장소의 코드가 낸 측정값이다. 측정하지 않은 것은 "목표"라고 적었다. 고객, 계약서, 사건은 전부 가상이다.

## 1. 문제

교란(태풍, 항만 적체, 자사 시스템 장애)이 생기면 관제실은 **마감 임박 순**으로 배차한다. 그런데 배상이 발생하는 순서는 마감 순서가 아니다. 같은 지연이라도 계약마다 결과가 다르다.

- 태풍이면 어떤 계약은 불가항력으로 **면책**되고, 어떤 계약은 "사유를 불문하고" 배상 의무가 발생한다.
- 면책 조항이 있어도 **12시간 안에 서면 통지**를 안 했으면 못 쓴다. 또 "대체 운송수단 확보 노력을 입증"해야 쓰는 조항도 있다.
- **유예**(24시간 이내 지연은 지체로 보지 않음)와 **상한**(화물가액의 10%)이 있는 계약은 한 사이클 더 기다려도 손해가 안 늘어난다. 상한이 없는 시간당 요율 계약은 매 시간 배상금이 누적된다.

이 차이를 사람이 사고 중에 계약서 8부를 펴 놓고 계산할 수는 없다. 그래서 급한 것부터 보내고, 배상은 정산 때 안다.

## 2. 통찰과 해법

**통찰.** 교란 때 필요한 질문은 "어느 화물이 급한가"가 아니라 **"한 사이클 더 보류하면 어느 계약에서 얼마의 배상이 추가로 발생하는가"**다. 이 값을 '배상 노출액'이라 부른다.

**해법.** ClauseTower는 세 단계로 이 값을 만들고, 네 번째 단계에서 증명한다.

| 단계 | 누가 | 하는 일 |
| --- | --- | --- |
| ① 계약 읽기 | LLM | 계약서 전문에서 요율·단위·유예·상한·불가항력 조항을 구조화한다. 모든 항목에 **조항 번호와 원문 인용**이 붙는다 |
| ② 면책 판단 | LLM | 이번 사건이 각 계약의 면책 사유에 해당하는지, 통지 시한과 정성 조건을 충족했는지 판단한다. 최종 적용 여부는 조건을 **기계적으로 결합**해 확정한다 |
| ③ 노출액 산출 | 결정적 코드 | 지연 시간을 넣으면 유예·단위 올림·영업일·누진·정액·상한을 순서대로 적용해 금액과 **계산 단계 문장**을 낸다. LLM은 여기 들어오지 않는다 |
| ④ 배차와 증명 | 시뮬레이터 | 트럭이 빌 때마다 '배상 노출액'이 큰 화물부터 보낸다. 같은 화물·같은 교란에서 기존 정책과 총 배상금을 비교한다 |

돈 계산을 LLM에 맡기지 않는 것이 설계의 핵심이다. LLM은 읽고 판단하고, 코드가 계산하고, 시뮬레이터가 심판한다.

## 5. 실제 모델로 돌린 결과

위 데모 숫자는 계약 조건에 정답지를 쓴 것이다(mock 모드). 실제 Claude(`claude-code` 모드, claude-opus-5-5)로 계약서 8부를 읽히고 두 시나리오의 면책을 판단시킨 결과는 다음과 같다(`eval/results/extraction_*.json`, `eval/results/real/`).

| 항목 | 결과 |
| --- | --- |
| 계약 조건 추출 정확도 | 106개 항목 중 102개 일치, **96.2%** |
| 면책 판단 정확도 | 태풍 32개 항목 **100%**, 항만 적체 32개 중 31개 **96.9%** |
| 인용 원문 일치율 | **100%** (모델이 쓴 인용 전부가 계약서 문장 그대로) |
| LLM 호출 | 추출 8회 + 판단 16회 = 24회, CLI가 보고한 비용 $1.98, 호출 시간 합계 270초(4개 병렬) |
| mock 대체(fallback) | 0회 |

틀린 4개 항목은 전부 `fm_conditions`(면책의 정성 조건 개수)다. 모델이 "서면 통지"나 "지체 없이 통지" 같은 통지 요건을 정성 조건으로도 한 번 더 적었다. 금액 계산에는 영향이 없었고, 태풍 시나리오의 정책 비교 결과는 정답지와 완전히 같았다.

판단이 갈린 1건은 항만 적체에서 누리에너지다. 정답지는 "합리적으로 통제할 수 없는 사유"로 면책을 봤고, 모델은 조건 미충족으로 면책을 보류했다. 보수적인 쪽(배상금을 잡는 쪽)으로 틀렸고, 그 결과 실제 모드의 항만 적체 기존 배상금이 810만 원으로 정답지(477만 원)보다 높게 잡혔다. 실제 운영에서는 이런 건을 사람이 확인하도록 "판단 근거" 카드에 이유가 적혀 나온다.

## 5-1. 웹 데모와 실제 케이스 분석

GitHub Pages(`https://namojo.github.io/clausetower/`)에 올린 웹 데모는 서버 없이 브라우저 안에서 시뮬레이션이 돈다. 파이썬 계산기와 시뮬레이터를 JavaScript로 옮겼고, 같은 입력에서 같은 총 배상금이 나오는지 `scripts/verify_engine.js`가 31개 항목을 대조한다(전부 일치).

심사위원이 직접 바꿀 수 있는 것: 계약 읽기 출처(정답지 또는 실제 Claude 추출), 화물 배치 5종, 고객 통지 시점, 트럭 수, 결항 대수와 시각, 피해 노선 배율, 입증 자료 같은 사실 관계, 그리고 고객별 면책 판단을 사람이 뒤집는 것. 값을 바꾸면 면책 적용 여부가 조건 결합으로 다시 계산되고 모든 화면이 갱신된다.

![웹 데모 조작 패널](screenshots/web/web_overview.png)

**실제 케이스 분석.** 계약서(txt, md, docx 또는 붙여넣기)를 올리면 LLM이 조건을 추출하고 현재 사건의 면책을 판단한 뒤 가상 화물 7건과 함께 시뮬레이션에 들어간다. 사건을 직접 적으면 8개 계약의 면책을 다시 판단한다. 연결 방식은 세 가지다.

| 연결 방식 | 어떻게 | 언제 |
| --- | --- | --- |
| Anthropic API 키 | 브라우저가 api.anthropic.com을 직접 호출. 키는 브라우저에만 저장 | 개인 키가 있을 때 |
| 로컬 도우미 | PC에서 `python -m clausetower serve --llm claude-code`. 브라우저가 127.0.0.1로 요청하고 도우미가 기존 파이프라인으로 처리 | Claude 구독(Claude Code CLI)으로 쓸 때, 사내 LLM을 중계할 때 |
| 사내·호환 엔드포인트 | OpenAI 호환 또는 Anthropic 호환 게이트웨이를 브라우저에서 직접 호출 | 사내 LLM이 CORS를 허용할 때 |

아래는 로컬 도우미를 Claude 구독으로 띄우고 예시 계약서를 올린 실제 실행이다. 추출에 22초가 걸렸고, 요율·유예·상한·면책 사유·통지 시한을 모두 맞게 읽었으며 인용은 원문과 일치했다.

## 5-2. 화면 설계 원칙

관제실 화면은 "숫자를 읽는 곳"이라 장식보다 위계와 밀도를 다뤘다.

- **고정 상황 패널(왼쪽).** 사건(유형·설명 직접 입력, 통지 시점, 사실 관계), 운영(트럭·결항·노선 배율), 화물 배치와 계약 읽기 출처, 그리고 고객별 면책 판단을 사람이 "자동 / 적용 / 미적용 + 이유"로 정하는 편집기. 값을 바꾸면 오른쪽 전체가 즉시 다시 계산된다.
- **조치가 먼저, 설명은 그 다음.** 상황 요약과 KPI → 지금 조치(보낼 화물·보낼 통지·성립시킬 면책) → 배상 노출 순위 → 추이와 정책 비교 → 계약 케이스(카드 또는 비교표) → 실제 케이스 분석 → 간트와 기록. 운영자가 사건 직후 첫 화면에서 해야 할 일을 끝내고, 아래로 내려가며 근거를 확인하는 순서다.
- **계약은 항목 격자로.** 과금 방식, 유예, 상한(막대), 기준금액, 불가항력 사유 칩, 통지 시한, 정성 조건, 이번 사건의 판단과 이유, 정책별 배상금을 한 카드에 고정 위치로 둔다. 비교표는 같은 항목을 고객 × 항목 행렬로 보여 준다.
- **근거는 한 번의 클릭, 항목 단위로.** 카드의 항목, 비교표의 칸, 조치 보드의 "조항 보기", 순위표의 "계약 항목별 상세"가 모두 같은 서랍을 그 항목에서 연다. 서랍은 항목별(값·뜻·조항·인용·판단 체크리스트)과 전문(인용 강조) 두 탭이고 "원문에서 보기"로 건너뛴다.
- **상태는 색이 아니라 글자와 아이콘으로.** 면책 적용(✓ 초록), 미적용(! 빨강), 조항 없음(– 회색)에 모두 글자 라벨이 붙는다. 사람이 뒤집은 판단은 "사람 결정"으로 표시된다.
- **서체와 숫자.** IBM Plex Sans KR과 표 숫자(tabular numerals)로 금액 자릿수가 세로로 맞는다. 색은 ClauseTower 파랑, 기존 주황, 상태 3색만 쓴다.

## 6. 아키텍처

```
contracts/*.md ──(LLM extract)──▶ PenaltyTerms + 인용 ─┐
scenarios/*.yaml ─(LLM judge)──▶ ForceMajeureJudgment ─┼─▶ exposure.py(결정적 계산기) ─▶ Breakdown(금액 + 계산 단계 + 인용)
                                                         │
sim.py: 트럭이 빌 때마다 정책이 다음 화물을 고른다 ◀──────┘   정책 = 마감 순 | 도착 순 | 고액 순 | 배상 노출 순위 | 탐색 근사 최적
        └─▶ PolicyResult(총 배상금, 지연 건수, 간트, 누적 곡선)
agent.py: 위를 묶어 Report(JSON) ─▶ dashboard.py(단일 HTML, 오프라인) / eval
```

- **스키마가 계약이다.** `schemas.py`를 바꾸면 대시보드와 eval이 함께 바뀐다.
- **법령·요율 수치는 코드에 없다.** 전부 계약서에서 추출한 `PenaltyTerms`에 있고, 계산기는 그것만 믿는다.
- **LLM 모드.** `mock`(정답지, 네트워크 없음), `claude-code`(Claude Code CLI, API 키 없이 구독), `anthropic`(SDK). 기본 `auto`.
- **배상 노출 순위의 정의.** 한 사이클 보류했을 때 늘어나는 배상금을 그 화물이 트럭을 묶는 시간으로 나눈 값. 절대값 변형도 함께 돌려 비교한다. 30개 시드 평균은 시간당 쪽이 조금 낮았고, 개별 실행에서는 절대값 쪽이 낮은 경우도 있다(위 표의 태풍이 그렇다).

## 7. 사업 연결

- 운송 계약의 지체상금·SLA 감액은 물류 사업의 손익에 직접 닿는 항목이다. 이 도구는 그 노출을 사고 중에 실시간으로 보여 준다.
- 물류 플랫폼의 예외 관리 화면에 "지금 배상 노출액" 열 하나를 더하는 형태로 들어갈 수 있다. 배차 엔진을 바꾸지 않고 우선순위 입력만 바꾼다.
- 제안·계약 단계의 위험 조항 검토(RFP Compass)와 같은 추출·인용 원칙을 쓴다. 계약 체결 전 위험 조항 경고와 체결 후 운영 중 노출 관리가 하나의 선으로 이어진다.

## 8. 위험과 대응

| 위험 | 대응 |
| --- | --- |
| "계약 해석을 AI에 맡기느냐" | 최종 결정은 사람. 에이전트는 노출액과 **조항 원문**을 보여 주는 참모다. 면책 적용 여부는 조건을 기계적으로 결합해 확정하고, 틀릴 때는 보수적인 쪽으로 틀리게 프롬프트했다 |
| 시뮬레이터가 단순하다 | 허브 하나, 노선 8개, 트럭 8대, 화물 56건. 결론은 "이 모형에서 순서만 바꿔 58~77% 절감"이지 실제 네트워크의 절감률이 아니다. 실제 TMS 데이터로 다시 재야 한다 |
| 정답지를 팀이 썼다 | 계약서와 정답지를 같은 사람이 만들었다. 실제 계약서로 블라인드 평가가 필요하다 |
| 데모 중 LLM 지연·실패 | 호출이 실패하면 정답지로 대체하고 로그에 남긴다(fallback 횟수를 보고서에 표시). 데모는 mock으로도 전부 돈다 |

## 9. 지금 안 되는 것과 다음

- 한국어 계약서만 다뤘다. 영문 계약서, 표로 된 요율표, 첨부 SLA 문서는 시험하지 않았다.
- 교란은 세 종류, 고객은 여덟이다. 복수 교란 동시 발생, 부분 적재, 환적은 모형에 없다.
- 탐색 근사 최적은 지역 탐색이라 진짜 최적이 아니다. 작은 사례에서 정확한 최적과 비교하는 것이 다음 과제다.
- 실제 모드 측정은 2개 시나리오, 1회 실행이다. 반복 실행으로 분산을 재야 한다.
- 다음 단계(목표): 통지 시한이 임박한 고객을 먼저 알리는 "통지 알림", 입증 자료(대체 운송 시도 기록)를 사고 중에 자동 수집하는 기능, 실제 TMS 이벤트 스트림 연동.
